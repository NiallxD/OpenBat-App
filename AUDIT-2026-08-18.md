# Efficiency + correctness audit — 2026-08-18

**Status legend:** ✅ implemented · 🔍 found, not fixed

## Summary

Nine changes went in (all building clean); fifteen bugs and six efficiency
findings are written up but not acted on, four of which need a decision from you.

**The two findings that matter most** are both silent-wrong-answer bugs rather
than performance ones:

- **B1** — every imported WAV that isn't shaped exactly like one OpenBat wrote is
  read as garbage. Four readers hardcode "PCM starts at byte 44, 16-bit, mono";
  the importer byte-copies whatever the user picked, and the picker accepts AIFF
  and `.audio`. A file from another detector with a `LIST` chunk — which is most
  of them — shows a noise spectrogram and plays as static, with no error.
- **B2** — species identification hardcodes 384 kHz. The classifier protocol has
  no sample-rate parameter, so on the built-in mic (48 kHz), on an iOS-clamped
  Griff, or in demo mode driven from a library recording, the model is handed a
  window it misreads by the rate ratio and returns confident-looking species
  names computed from a spectrogram whose frequency axis is wrong by up to 8×.

The largest *efficiency* problem was item 1 from the earlier pass and is now
fixed: the recorder was doing roughly 800 MB/s of memmove, continuously, whether
or not anything was being recorded.

Nothing in this pass changes listening modes, classifier models, the upload or
consent path, the field-guide schema, or release status, so no documentation
propagation was needed. **B1, B2 and B3 would each need it if acted on** — B2 in
particular touches what the app claims about species identification.

## Part 1 — Implemented this session

### ✅ E1. Pre-roll buffer was ~800 MB/s of memmove, continuously
`Audio/AudioRecorder.swift`

The 3-second pre-trigger buffer was an Array appended at the back and trimmed
from the front. Trimming the front of an Array shifts everything behind it: at
384 kHz that is a 4.6 MB shift, once per capture callback (~188/s), i.e. of the
order of **800 MB/s of pure memmove on a `.userInitiated` queue**, running
whenever capture was up — armed or not, since only demo mode gated the path.

Replaced with a fixed ring: two memcpys of the incoming buffer, independent of
pre-roll length.

Kept running while disarmed **deliberately** (I'd floated skipping it): with the
ring the cost is negligible, and skipping would mean arming just as a bat passes
gives a truncated pre-roll — the exact case the pre-roll exists for. Pure win,
no behaviour change.

Incidental correctness fix: the ring is rebuilt on a capture-rate change. The
Array version carried pre-roll samples across a rate change, so a segment opened
just after a mic swap spliced audio captured at the old rate into the head of a
file written at the new one — wrong duration and wrong pitch for the first
seconds. Also made the pre-roll length setting take effect without discarding
history (`preRollWindow` reads a window rather than enforcing a cap on write).

### ✅ E2. Capture hand-off copied 384 000 samples/second one at a time
`Audio/AudioRecorder.swift`

`append()` runs on the realtime audio thread and moved samples into the SPSC
ring with a per-sample loop, modulo and branch each. Replaced with up to two
block copies, matching the read side in `drainCapture` and the PCM ring in
`SpectrogramProcessor`. Drop-when-full policy preserved exactly.

### ✅ E3. Whole pass log re-encoded and rewritten on every finished pass
`Classifier/ClassificationStore.swift`

`passes` is capped at 500 records, each carrying every contributing pulse and its
six top scores — on the order of a megabyte of JSON. It was fully re-encoded and
atomically rewritten every time a pass closed, i.e. every few seconds during real
activity.

All three stores now share one coalescing throttle (5 s). Notably this is a
*coalescing* throttle, not the drop-on-throttle one sessions already had:

> 🔍 **Bug found in passing:** the old `persistSessions(force:)` silently dropped
> any unforced save inside its window rather than deferring it. The last
> breadcrumb of a burst never reached disk unless something forced a write
> afterwards. Fixed by the same change.

Deletions and manual species edits now force a write (files leave disk
immediately; the index must not outlive them). `flushPendingWrites()` is called
from `ContentView` when the scene leaves `.active`, so a deferred save lands
before a force-quit or jetsam kill.

**Build:** `** BUILD SUCCEEDED **` after all three.

## Part 2 — Audit findings

### 🔍 B1. **HIGH** — Every imported WAV that isn't byte-identical in shape to one OpenBat wrote is read as garbage
`Audio/WavHeader.swift`, `Audio/WavPCMReader.swift`, `DSP/STFTGrid.swift`,
`Audio/PlaybackEngine.swift`, `Audio/RecordingImporter.swift`, `SessionsView.swift`

Four separate readers hardcode the same three assumptions: the PCM starts at
**byte 44**, samples are **16-bit**, and the file is **mono**.

```
handle.seek(toOffset: UInt64(44 + startSample * 2))
```

That is exactly and only true of files `AudioRecorder` writes. But the import
path byte-copies whatever the user picked and renames it `.wav`, with the picker
declaring `allowedContentTypes: [.wav, .aiff, .audio]`. Validation is
`AVAudioFile(forReading:)` succeeding — which succeeds for all of:

| Imported file | What happens |
|---|---|
| WAV with a `LIST`/`INFO` chunk before `data` | PCM read from the wrong offset; if that offset is odd, samples are byte-swapped into noise |
| WAV with `WAVE_FORMAT_EXTENSIBLE` (40-byte `fmt `) | same, offset out by 24 |
| Stereo WAV | channels read as consecutive mono samples |
| 24-bit / 32-bit float WAV | garbage |
| AIFF (explicitly allowed) | big-endian, different header — garbage |
| `.m4a`/`.mp3` (matched by `.audio`) | garbage |

The extra-chunk case is not exotic: Audacity, Wildlife Acoustics and Pettersson
all commonly write `LIST` chunks. Those are precisely the files the importer's
own header comment says it exists for — "a reference recording, something from
another detector, a call library download".

**What the user notices:** an imported recording shows a noise spectrogram and
plays as static, with no error. The app's own recordings are always canonical,
so this never shows up in normal use or in the test suite.

`WavHeader.read` has the same shape: `dataBytes` is read from a fixed offset 40,
correct only when `data` immediately follows a 16-byte `fmt `.

**Fix:** parse the RIFF chunk table once on import (locate `fmt ` for
channels/bits/rate, locate `data` for its offset and length), and either store
that geometry alongside the recording for all four readers to use, or — simpler
and safer — transcode on import to the canonical 16-bit mono form the rest of
the app already assumes, and reject what can't be transcoded. The picker's
content types should also stop advertising AIFF unless it's converted.

### ✅ B2. **HIGH** — Species identification silently assumes the input is 384 kHz
> **Resolved 2026-08-18, decision 1 answered: refuse-and-don't-say-so.** The
> detector now declines to classify off the model's native rate; the pass closes
> as NoID and nothing else about the pulse changes. Deliberately not surfaced in
> the UI — the pulse detector's own 15 kHz floor against a 24 kHz Nyquist on the
> built-in mic leaves almost nothing that could trigger, so the reachable failure
> window is narrow. See `Context.md` §9.

`Classifier/BatDetect2Classifier.swift:94`, `Classifier/BatClassifier.swift:118`,
`Classifier/NaBatSpectrogramRenderer.swift`

The classifier protocol is `classify(pcm:gate:prior:)` — **no sample rate**. So the
one object that knows the true capture rate (`PulseDetector`, which uses it
correctly everywhere else) has no way to tell the classifier, and both models
hardcode 384 kHz:

- BatDetect2: `PolyphaseResampler.resample(pcm, from: 384_000, to: …)`
- NABat: `NaBatSpectrogramRenderer.render(pcm: pcm)` — the function *does* take a
  `sampleRate:` parameter and override `spec.sampleRate` with it, but the single
  call site doesn't pass one, so it takes the 384 000 default.

Meanwhile `PulseDetector.scheduleCapture` sizes the window from the **real** rate
(`Int(inputSpec.windowSeconds * sr)`). So the two ends disagree: the detector
hands over 0.05 s of audio measured in real samples, and the classifier reads it
as 0.05 s of 384 kHz audio. At 48 kHz that is 2 400 samples where NABat expects
19 200 — 22 STFT frames stretched across a 100-frame image, with the frequency
axis wrong by 8×.

There is no guard. Nothing disables or flags AutoID when the rate isn't native.

**Three ways a user reaches this today:**
1. **No Griff attached.** The app runs on the built-in mic at 48 kHz — it warns
   about the rate in the mic pill but classifies anyway.
2. **iOS clamps the Griff to 48 kHz.** This is the exact failure the delivered-rate
   debounce in `AudioEngineController` exists to detect and report.
3. **Demo mode driven from a library recording.** `DemoModeView` offers every
   recording in the library, imported files included, at whatever rate they are.

**What the user notices:** confident-looking species names that are wrong, with
no indication anything is off. This is worse than no ID — a wrong ID in the
Sessions log is indistinguishable from a right one, and it is eligible for
upload to the community dataset.

**Fix:** add the rate to the `SpeciesClassifier.classify` signature and thread it
through from `PulseDetector` (it already has `sampleRate` in scope at the call).
Note that for NABat, overriding `spec.sampleRate` alone is only half a fix: its
`nFFT = 384` is itself derived from the rate (`int(0.001 * 384000)`), so the
window duration also has to be recomputed. Given that, the honest short-term fix
may be to **refuse to classify** off-native input and say so, rather than to
produce a resampled approximation of a pipeline that was validated at one rate.
That's a decision below.

### 🔍 B3. **MEDIUM** — The measured 96 kHz capture artifact is never filtered, and the filter written for it is dead code
`DSP/Biquad.swift:69`, `TimeExpansion/SnippetExpansionProcessor.swift`,
`TimeExpansion/TimeExpansionProcessor.swift`

`Biquad.notch` carries a precise, measured bug report in its doc comment:

> the capture path injects a narrowband tone at **inputSampleRate / 4** — 96.0 kHz
> at 384 kHz, sitting +11 dB above the local noise floor in every recording
> checked … any mode that divides frequency maps it straight into the audible band
> as a steady whine (12 kHz at ÷8, 6 kHz at ÷16).

**`Biquad.notch` has zero call sites.** The filter was written and never wired up.

Both frequency-dividing modes are affected and neither removes it:
- `SnippetExpansionProcessor` applies a 12 kHz high-pass and (only when N < 8) an
  anti-alias low-pass. At the default N = 8 the replay step is exactly 1.0 and
  96 kHz lands at 12 kHz.
- `TimeExpansionProcessor` is a straight pass-through with only the user's band
  filters; the same tone lands at 12 kHz in file playback.

Heterodyne is not affected — 96 kHz mixes to a difference far above its 4 kHz
low-pass.

**What the user notices:** a steady tone under every slow replay and every
time-expanded playback, at a pitch that sits right in the ear's most sensitive
region.

### 🔍 B4. **MEDIUM** — Closing a recording blocks the recorder queue on a full-file FFT, dropping live audio
`Audio/AudioRecorder.swift` — `closeAndKeep`

`closeSegment` → `closeAndKeep` calls
`RecordingSpectrogramRenderer.render(wavURL:maxWidth: 4096)` **synchronously on
the recorder queue**. That queue is also the one draining the capture ring. While
the render runs, nothing drains, and the ring holds **1.4 s** of audio.

A whole-file FFT overview of a long segment is not fast — `maxSegmentSeconds` is
600, so a rotated segment can be 230 M samples. Even an ordinary 10 s segment is
a few million samples.

Two consequences, both silent:
- Capture buffers are dropped once the ring fills, so audio is lost from the
  moment the previous recording closed.
- The segment-rotation path (`closeSegment(); if armedQ && activeQ { startSegment() }`)
  starts the next file immediately after the render, so the next recording is
  missing its own opening.

**Fix:** hand the render to a separate queue and report the `Recording` when it
finishes (the report is already asynchronous via `onRecordingSaved`), or report
with no image and fill it in later. Nothing about the render needs to be
serialized against capture.

### 🔍 B5. **LOW-MEDIUM** — Recorder settings are written from the main thread and read from the recorder queue
`Audio/AudioRecorder.swift`, `SettingsView.swift:495,503`

`preRollSeconds`, `postRollSeconds` and `maxSegmentSeconds` are plain
`@Observable`-tracked `var`s bound straight into sliders
(`Slider(value: $recorder.preRollSeconds, …)`) and read on the recorder queue in
`handle`, `setPulseActive` and `appendPreRoll`. Unsynchronized cross-thread
access to `@Observable` stored properties — the registrar is thread-safe, the
stored value isn't.

Every other cross-thread setting in the audio layer goes through a lock
(`HeterodyneProcessor.ctrlLock`), an atomic, or a `queue.async` setter
(`setPassGates`, `setCoordinate`). These three are the exception.

**Fix:** the pattern already exists in this same file — a `setPreRoll(_:)` style
setter that hops onto `queue`, with the UI binding writing through it.

### 🔍 B6. **LOW** — A full disk produces ~188 main-thread dispatches a second
`Audio/AudioRecorder.swift` — `write`

Once `segmentWriteFailed` is set the segment is doomed, but `write` keeps being
called for every subsequent buffer, keeps failing, and keeps assigning
`lastWriteError` — whose `didSet` dispatches to the main thread each time. At
384 kHz that's ~188 main-thread hops a second for the rest of the post-roll,
exactly when the device is already in trouble.

**Fix:** early-return from `write` when `segmentWriteFailed` is already set.

### 🔍 B7. **LOW** — The WAV header and the GUANO chunk can disagree about the sample rate
`Audio/AudioRecorder.swift`

The RIFF `fmt ` chunk gets `UInt32(sr)` (truncating) and GUANO gets
`String(Int(sr.rounded()))`. For any non-integral delivered rate the file's two
statements of its own sample rate differ by 1 Hz. Harmless today (rates are
integral) but it's a latent inconsistency in a file format other tools parse.

### 🔍 B8. **LOW** — DC offset inflates FFT bin 0, which drives the display's adaptive contrast
`Spectrogram/SpectrogramProcessor.swift` — `makeColumn`

`vDSP_fft_zrip` returns a packed split-complex result where `realp[0]` is DC and
`imagp[0]` is Nyquist, so `vDSP_zvabs` makes `magnitudes[0] = sqrt(DC² + Nyquist²)`
— bin 0 conflates the two.

Bin 0 is correctly excluded from the **peak/trigger** search (`minBin = max(1, …)`),
so detection is unaffected. But the adaptive display ceiling is taken over every
bin:

```swift
vDSP_maxv(magnitudes, 1, &columnMaxLog, n)   // n = binCount, includes bin 0
```

The app measures DC offset as a mic-QA metric precisely because it occurs on this
hardware. When it's large enough to clear the −40 dB ceiling floor, bin 0 pulls
`runningCeilingDB` up and the whole live spectrogram loses contrast — for a
reason that has nothing to do with signal.

**Fix:** take the ceiling over the same band the peak search uses, or zero
`imagp[0]` before `zvabs`.

### 🔍 B9. **LOW** — Scrolled-back spectrogram samples one texel past what was uploaded
`Spectrogram/SpectrogramRenderer.swift`, `Spectrogram/Spectrogram.metal`

On the seek path `rightEdge = Float(vc)` and `vc` columns are uploaded into
`[0, vc)`. The shader maps `uv.x = 1` to `u = vc/texWidth`, which is the boundary
between texel `vc-1` and texel `vc` — one past the uploaded region. With linear
filtering the rightmost pixel column is a 50/50 blend with whatever the
double-buffered seek texture held previously.

**What the user notices:** a one-pixel stripe of stale data at the right edge
while scrubbing. `rightEdge` should be `Float(vc) - 0.5`. The live ring path
doesn't have this — its display head is held ~45 columns behind the write head.

### 🔍 B10. **LOW** — `Dictionary.max(by:)` ties break nondeterministically
`Classifier/PassAggregation.swift:91,106`, `Classifier/PulseDetector.swift:397`

Winning species, and the runner-up suggestion, are chosen with `max(by:)` over a
`Dictionary`. Swift seeds dictionary hashing per process, so an exact tie
resolves differently between launches. Vanishingly rare with float scores, but it
means the same recording can in principle re-classify differently, which is a
surprising property for a log people compare.

### 🔍 B11. **LOW** — Four types are missing the `nonisolated` their siblings all carry
`Classifier/PulseImageRenderer.swift`, `ClassifierSpectrogramEngine.swift`,
`NaBatSpectrogramRenderer.swift`, `BatDetect2SpectrogramRenderer.swift`,
`DSP/PolyphaseResampler.swift`

The project sets `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor`, so these are
main-actor isolated, and every one of them is called only from a background
queue. `Biquad`, `AudioLevel`, `WavHeader`, `WavPCMReader`, `STFTGrid`,
`PassAggregation`, `BatClassifier`, `GuanoMetadata` and
`RecordingSpectrogramRenderer` all carry an explicit `nonisolated` with a comment
explaining exactly this; these five were missed.

Not currently a live bug — `SWIFT_VERSION = 5.0` makes it a warning, each has a
single caller, and `PulseImageRenderer`'s static scratch buffers are in fact only
touched from one serial queue. But that invariant is now load-bearing and
unstated, and the annotation is what states it.

### 🔍 B12. **LOW** — Stale comments in the pulse renderer
`Classifier/PulseImageRenderer.swift`

The header describes the live display as "fftSize 1024 / hop 512 → 750
columns/sec" (it is 2048 / 256 → 1500), and line 207 says "this renderer's bin
count is small (fftLen/2 = 512)" when `fftLen` is 2048 and the bin count is 1024.
Both date from before the FFT was resized. The second matters a little because it
is the justification given for rendering the full spectrum every time — at 1024
rows the cost is 4× what the comment claims.

## Part 3 — Efficiency findings (beyond the three implemented)

### 🔍 E4. **HIGH** — The "polyphase" resampler isn't polyphase; it does ~6× the arithmetic it needs
`DSP/PolyphaseResampler.swift`

The math is correct — I checked the sinc, the Kaiser window, the `vDSP_conv`
correlation-vs-convolution reversal, the group-delay offset and the output
count, and all of them are right. The *structure* is the naive
zero-stuff → full-convolve → decimate form the file's own name says it isn't.

For the app's only ratio (384 → 256 kHz, up=2 down=3) on a 0.256 s BatDetect2
window (98 304 samples), each classified pulse does:

- allocate `upsampled` — 196 608 floats
- allocate `padded` via **two array concatenations** — another ~196 728 floats
- allocate `convolved` — 196 668 floats
- a 61-tap convolution over 196 608 samples ≈ **12 M multiply-adds**, of which
  half the input taps are multiplying zeros the zero-stuffing just inserted
- then throw away two out of every three outputs

A real polyphase decomposition computes only the outputs it keeps, using only
the non-zero taps: ~2 M MACs and no intermediate arrays. Roughly **6× less
arithmetic and ~2.4 MB less allocation per classified pulse**, on the capture
queue, while live detection continues.

(`h.reversed() as [Float]` also reallocates the 61-tap filter on every call,
defeating half the point of `filterCache`. Trivial next to the above.)

### 🔍 E5. **MEDIUM** — The classifier's median denoise copies the data, then the callee copies it again and sorts
`Classifier/ClassifierSpectrogramEngine.swift` — `rowThenColumnMedian`, `sortedMedian`

The row pass goes to real trouble to copy each row into a reused `tmp` buffer
with `withUnsafeMutableBytes`/`copyMemory`. It then calls:

```swift
private static func sortedMedian(_ buf: inout [Float], count: Int) -> Float {
    var tmp = Array(buf.prefix(count))   // allocates + copies again
    tmp.sort()
    …
}
```

The `inout` is never used — the function doesn't mutate `buf` — and the careful
memcpy into the reusable scratch is immediately undone by a fresh allocation.
For NABat that's **393 array allocations and 393 sorts per classified pulse**
(one per bin, one per frame).

A partial selection (`quickselect`/nth_element) in place would be O(n) rather
than O(n log n) *and* allocation-free. Even just dropping the redundant copy is
most of the win.

### 🔍 E6. **MEDIUM** — Mic calibration is applied with a scalar loop on the realtime audio thread
`DSP/MicCalibrationCurve.swift` — `apply(to:)`

```swift
for i in 0..<binCount { magnitudes[i] *= gains[i] }
```

Called from `SpectrogramProcessor.makeColumn`, i.e. **1 500 times a second at
1 024 bins — 1.5 M scalar multiplies per second on the realtime audio thread**,
whenever a calibration is active. This is a single `vDSP_vmul`, and every
neighbouring line in `makeColumn` is already vectorised for exactly this reason.

Also: `apply(to:)` guards `magnitudes.count == binCount` but **not**
`gains.count == binCount`. `MicCalibrationCurve` is `Codable` and persisted, so
a truncated or version-skewed curve would index out of range — a crash on the
realtime audio thread, from data on disk. One cheap guard.

### 🔍 E7. **MEDIUM** — Every captured pulse renders ~500 000 pixels to display ~70 000
`Classifier/PulseImageRenderer.swift`

The rendered image is `wideOutFrames × renderBins` = 480 × 1023 ≈ **491 000
pixels**, built one at a time with a LUT lookup and four byte writes, then copied
again into a `Data` for the `CGDataProvider` (~2 MB per pulse). The pulse view
displays it at roughly 350 × 200 points.

The full height exists so pinch-zoom-out can reach full spectrum, which is a
real feature — but note the comment justifying the cost says "this renderer's bin
count is small (fftLen/2 = 512)", and `fftLen` is 2048, so the bin count is 1024
and the cost is **4× what that reasoning assumed** (see B12).

During a busy pass this runs several times a second on the capture queue.

### 🔍 E8. **LOW** — Two remaining scalar loops on the realtime audio thread
`Audio/AudioDiagnostics.swift` — `AudioLevel.analyze`, and
`Heterodyne/HeterodyneProcessor.swift` — `process`

- The clipped-sample counter is a scalar loop over every sample (384 k/s)
  sitting between three vectorised Accelerate passes. `vDSP_vclipc` returns the
  count of clipped values as part of a vectorised clipping pass.
- The heterodyne mixer calls double-precision `cos()` **once per input sample** —
  384 000 libm calls a second. A complex-rotation recurrence (with periodic
  renormalisation) or an interpolated phase table is a few multiplies. Small in
  absolute terms — well under 1% of a core — but free to fix and it is on the
  realtime thread.

Both are minor next to E1–E3; listing them for completeness since the realtime
thread is where this project already holds the line.

## Part 4 — Verified correct (checked, no action)

Recording these so the next pass doesn't re-derive them:

- **`PolyphaseResampler`'s filter math.** Windowed-sinc cutoff normalisation, the
  `h *= up` DC compensation, `vDSP_conv`'s correlation-vs-convolution reversal
  and zero-padding, the `halfLen` group-delay offset, and `outCount` are all
  correct. Only the structure is wasteful (E4).
- **`Biquad`'s RBJ coefficients** — lowpass, highpass and notch all match the
  cookbook.
- **`SnippetExpansionProcessor`'s ring/envelope arithmetic.** The
  envelope-block alignment with `writeCursor` holds across wraps (the ring is
  block-aligned by construction); the `replayStart` modulo is correct for
  negative operands; the fade-out threshold correctly converts output-time into
  input-samples via `step`; the `wasReplaying` handshake keeps `totalWritten`
  single-writer. The release/acquire publication of `replayStart`/`replayCount`
  through the phase atomic is a correct pairing.
- **`HistoryBuffer.rowMajorSlice`'s ring indexing**, including the double-modulo
  for arbitrarily negative operands, and its `available` guard.
- **`SpectrogramProcessor`'s absolute-sample accounting.** `accumAbsStart +
  accumulator.count == pcmTotalWritten` holds through the normal path and the
  suspended path.
- **`PassAggregation`'s means and gates**, including that `$0.key != noiseClassName`
  correctly keeps every candidate when `noiseClassName` is nil.
- **`PulseImageRenderer`'s geometry** — `hzPerBin`, the normalised −12 dB and
  −15 dB thresholds (dB converted into the 0–1 grid by dividing by
  `dynamicRangeDB`), the clean-crop rect bounds, and every loop bound against
  `nFrames`/`bins`.
- **`ClassifierSpectrogramEngine`'s `vDSP_vthres`** is the right call (clip
  negatives to zero), not the `vDSP_vthr` it resembles.

### 🔍 B13. **LOW** — A latent crash that fixing B2 naively would expose
`Classifier/ClassifierSpectrogramEngine.swift:145`

```swift
for bin in loBin...hiBin
```

is a `ClosedRange`, which traps if `loBin > hiBin`. With the sample rate
hardcoded at 384 kHz this is unreachable (always 6…99 for NABat). Thread a real
rate through as B2 requires and a low-rate source makes `loBin` exceed `hiBin` —
at 8 kHz it would be 241 > 191, a hard crash. Whatever shape the B2 fix takes,
this range needs a guard.

### 🔍 B14. **LOW** — The quality gate is inert for BatDetect2 but is presented as a setting
`Classifier/BatDetect2Classifier.swift:93`

`classify` takes a `gate:` and documents that it ignores it ("BatDetect2 has no
equivalent of NABat's quality-gate metrics defined yet"). If the AutoID settings
screen offers the quality-gate controls while BatDetect2 is the active model,
they are a control that does nothing — the same failure mode `CLAUDE.md`'s
simplified-view rule exists to prevent. Worth checking whether the UI hides them
per-model. _(Not verified in this pass.)_

### 🔍 E9. **LOW-MEDIUM** — The spectrogram renders at 60 fps while the detector is stopped
`Spectrogram/SpectrogramView.swift`, `ContentView.swift:1755`

The Metal view is paused for `menuIsOpen || section != .detector` — but **not**
for "capture isn't running". Sitting on the Detector tab before pressing Start,
or after Stop, the GPU runs a full-screen fragment pass 60 times a second over a
static image, and `draw(in:)` runs its drain loop and display-head integration
each frame.

Not a huge draw, but it is continuous and it is the screen the app sits on.

Pausing outright isn't quite right: with `enableSetNeedsDisplay = false` a paused
view also stops responding to scroll-back, which is still useful after a stop. So
this wants either "pause when idle **and** not scrolling" (needs
`SpectrogramView`'s private `isScrolling` lifted a level) or simply a lower
`preferredFramesPerSecond` when `!audio.isActive`. Small, but it's a design
choice about what the idle detector screen does, so I've left it.

### 🔍 B15. **LOW** — Comment claims a counter is rebased that never is
`Classifier/PulseDetector.swift` — `resetStats`

> a full engine restart rebases that counter — so a stale `pendingArmAbs` from the
> previous run compares against the new stream's indices as a wildly negative wait

`pcmTotalWritten` in `SpectrogramProcessor` is never reset, and the processor
outlives every engine restart (it's `@State` in `ContentView`), so the absolute
sample clock is monotonic for the whole process. The defensive clearing in
`resetStats` is harmless and worth keeping, but the stated reason is false — and
it's the kind of false premise someone later builds on.

## Part 5 — What I fixed in this pass beyond items 1/2/6

All build clean and none require a judgement call:

| | Fix |
|---|---|
| **B4** | Segment-close spectrogram render moved off the recorder queue onto its own `reportQueue`. Was blocking the capture drain for potentially seconds — dropping live audio, and truncating the start of the next file on the rotation path. |
| **B6** | `write` early-returns once the segment is already condemned. Was doing ~188 failed writes/s and ~188 main-thread hops/s on a full disk. |
| **B5** | `preRollSeconds`/`postRollSeconds`/`maxSegmentSeconds` now mirror into queue-local copies on write; the recorder queue reads only those. Removes an unsynchronised cross-thread read of `@Observable` stored properties. |
| **E6** | `MicCalibrationCurve.apply` is one `vDSP_vmul` instead of a 1024-iteration scalar loop running 1500×/s on the realtime thread — plus a `gains.count` guard, since the curve is decoded from disk and a short one would have indexed out of range there. |
| **B8** | The adaptive display ceiling is taken from bin 1 up, so the packed-FFT bin 0 (which conflates DC with Nyquist) can no longer flatten the live view's contrast when the mic has a DC offset. |
| **E8a** | `AudioLevel.analyze`'s clipped-sample loop is skipped entirely unless the already-computed peak magnitude says a clipped sample is possible — which on any non-clipping capture is never. Deliberately *not* `vDSP_vclipc`: that needs an output buffer, and a reusable one would mean static mutable state on a stateless enum touched from a realtime thread. |
| — | The pre-roll ring is sized for the **longest** pre-roll the slider offers rather than the current one, so moving the setting no longer reallocates or empties the buffer (`preRollWindow` narrows the read instead). The slider's upper bound now reads `AudioRecorder.maxPreRollSeconds` so the two can't drift. |

**Not covered by tests.** The pre-roll ring is the most intricate change and
`OpenBatTests` has no `AudioRecorder` coverage at all. I traced the index
arithmetic by hand for the wrap, the full-ring, the shortened-window and the
head-at-zero cases and it holds, but a round-trip test (feed N buffers, trigger,
assert the written samples are the last `preRollSeconds` worth in order) would be
worth having — it's the kind of thing that would fail loudly and is currently
only checked by listening to a recording's first three seconds.
`MicCalibrationTests` does exercise `MicCalibrationCurve`, so that one is worth a
run.

## Part 6 — Decisions for you

Ranked by what I'd want an answer on first.

**1. What should happen when the input isn't 384 kHz? (B2)**
Threading the real rate into the classifiers is mechanical, but it produces
*approximate* results from pipelines that were validated at one rate — and for
NABat the window length is itself derived from the rate, so it's not a one-line
change. The alternative is to refuse to classify off-native input and say so in
the UI. My instinct is refuse-and-say-so: a wrong species in the Sessions log is
worse than no species, and these results are eligible for upload. But that
removes AutoID from the built-in-mic and demo-from-library paths, which may be
how people try the feature first.

**2. Should imported files be transcoded on the way in? (B1)**
Parsing the RIFF chunk table properly and storing the geometry means four readers
change and every existing recording needs a default. Transcoding to canonical
16-bit mono on import means one place changes and everything downstream keeps its
current assumption — at the cost of not preserving the original bytes, which
matters if anyone imports a file intending to re-export it. I'd transcode.

**3. Wire up the 96 kHz notch? (B3)**
The filter exists and the artifact is measured. It changes what people hear in
two modes, so it's your call rather than mine. Worth confirming the tone is still
present on current hardware first — the measurement note isn't dated.

**4. Rewrite the resampler as an actual polyphase? (E4)**
~6× less arithmetic and ~2.4 MB less allocation per classified pulse, on the
capture queue. Self-contained, testable against the current implementation
output. Worth doing but nothing is broken.

Lower-stakes and safe to just do whenever: E5 (redundant copy + sort in the
median denoise), E9 (idle frame rate), B9 (one-pixel seek-texture edge), B13
(guard the `loBin...hiBin` range), B12/B15 (stale comments).
